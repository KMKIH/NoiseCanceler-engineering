# 곡 후반으로 갈수록 노트가 음원보다 앞당겨지는 문제

> 이 문서는 [FMOD 기반 리듬게임 시간 동기화 및 판정 시스템](../architecture/rhythm-game-timing-and-judgement-system.md)을 구축하기 전, Unity `AudioSource`를 사용하던 시기의 문제 해결 과정을 다룹니다.

## 개요

리듬게임을 테스트하던 중 곡 초반에는 정상적으로 보이던 노트가 후반으로 갈수록 음원보다 먼저 판정선에 도달하는 문제가 발생했습니다. 특정 노트에서 갑자기 싱크가 어긋나는 것이 아니라 곡이 진행될수록 오차가 커지는 현상이었습니다.

처음에는 노트 이동과 음원이 서로 다른 시간을 참조하는 구조를 원인으로 판단해 시간 기준을 통일했습니다. 그러나 긴 곡의 후반에는 미세한 오차가 남았습니다. 이후 노트 생성 로직에서 채보 데이터의 전처리 과정까지 추적했고, 마디 길이의 소수점 손실과 누적 계산이 남은 오차의 원인임을 확인했습니다.

## 문제 상황

노트는 생성 지점에서 판정 지점까지 정해진 시간 동안 이동합니다. 짧은 구간을 반복해서 확인할 때는 노트와 음악이 정상적으로 맞았지만, 곡 전체를 재생하면 뒤로 갈수록 노트가 음악보다 점차 빨라졌습니다.

```text
곡 초반  노트와 음원의 차이를 체감하기 어려움
곡 중반  노트가 음원보다 조금 먼저 판정선에 도달
곡 후반  노트가 앞당겨지는 현상이 뚜렷하게 나타남
```

특정 노트나 마디를 기점으로 갑자기 발생하는 문제가 아니었기 때문에 개별 채보 데이터의 오류보다는, 반복되는 시간 계산에서 작은 차이가 계속 더해지고 있을 가능성이 높았습니다.

## 원인 분석

### 노트와 음원이 서로 다른 시간 기준 사용

기존 노트는 Unity의 `Time.time`으로 생성 후 경과 시간을 구하고, 경과 시간과 이동 속도를 이용해 위치를 계산했습니다.

```csharp
double timeSinceStart = Time.time * 1000 - startTime;
float moveDistance = (float)(timeSinceStart * speed);
transform.position = startPoint.position + Vector3.left * moveDistance;
```

반면 음원은 오디오 시스템의 재생 시간에 따라 진행됐습니다. 노트와 음악이 서로 다른 시계를 사용하므로, 프레임 지연이나 두 시간값의 갱신 차이가 발생하면 노트의 위치가 음악과 어긋날 수 있는 구조였습니다.

이를 첫 번째 원인으로 보고 노트 이동의 시간 기준을 음원 재생 시간으로 변경했습니다. 눈에 띄던 이동 오차는 줄었지만, 곡 후반의 미세한 차이는 사라지지 않았습니다. 하나의 가설만으로 전체 현상을 설명할 수 없다고 판단해 노트가 사용하는 출현·판정 시각이 만들어지는 과정까지 조사 범위를 넓혔습니다.

### 정수 변환으로 인한 마디 시간 손실

채보 전처리 과정에서는 마디의 길이와 상대 시작 시각을 밀리초 단위의 `int`로 저장하고 있었습니다. BPM으로 계산한 마디 길이는 소수점 이하 값을 가질 수 있지만, 정수형으로 변환하면 그 값이 사라집니다.

예를 들어 한 마디의 실제 길이가 `1777.777ms`인데 `1777ms`로 저장된다면 마디마다 약 `0.777ms`가 손실됩니다.

```text
한 마디의 시간 손실      약 0.777ms
200마디에서의 손실 예시  0.777ms × 200 ≒ 155ms
```

한 마디만 확인하면 체감하기 어려운 차이지만, 잘린 값을 다음 마디의 시작 시각에 계속 더하면 곡이 진행될수록 채보 시간이 실제 음악보다 점차 빨라집니다.

처음에는 마디 길이와 상대 시작 시각의 자료형을 `int`에서 `float`로 변경했습니다. 그러나 수정 후에도 오차가 남았고, 계산 경로를 다시 확인한 결과 값을 만드는 식에 정수 변환이 그대로 남아 있었습니다.

```csharp
float barTakeTime = (int)(60f / bpm * beatPerBar * 1000);
```

결과를 `float` 변수에 저장하더라도 `(int)` 변환이 먼저 실행되므로 이미 사라진 소수점 이하 값은 복구되지 않았습니다.

### 잘린 마디 시간을 이전 값에 누적

기존에는 마디 시작 시각을 계산할 때 이전 마디까지 더한 `cumulativeTime`을 사용했습니다.

```csharp
relativeStartTime = cumulativeTime;
cumulativeTime += barTakeTime;
```

`barTakeTime`에서 발생한 정밀도 손실이 누적값을 통해 다음 마디의 기준으로 계속 전달됐습니다. 정수 변환과 누적 합산이 함께 사용되면서 한 번에는 작았던 오차가 곡의 길이에 비례해 커지고 있었습니다.

## 해결

먼저 노트의 생성 시각과 현재 시각을 음원 재생 시간으로 통일했습니다. 매 프레임 이동량을 더하는 대신, 현재 음원 시간이 전체 이동 구간에서 차지하는 비율로 절대 위치를 계산했습니다.

```csharp
float currentSongTime = SoundManager.Instance.GetMusicProgressInMs();
float ratio = (currentSongTime - startTime) / takeTime;

transform.position = Vector3.Lerp(
    startPoint.position,
    judgePoint.position,
    ratio);
```

프레임이 잠시 지연되더라도 다음 프레임에는 현재 음원 시간에 해당하는 위치를 다시 계산하므로, 노트가 음악과 다른 시간축을 따라가는 문제를 제거했습니다.

다음으로 마디 시간에 사용되는 자료형을 실수형으로 변경하고, 계산식에 남아 있던 정수 변환을 제거했습니다. 마디 시작 시각도 이전 값을 계속 더하는 방식에서 벗어나, 마디 인덱스와 정확한 마디 길이로 직접 계산했습니다.

```csharp
float barTakeTime = 60f / bpm * beatPerBar * 1000;
relativeStartTime = barIndex * barTakeTime;
```

각 마디의 시작 시각이 이전 마디의 계산 결과에 의존하지 않으므로, 앞에서 발생한 오차가 다음 마디로 전파되는 경로가 사라졌습니다. 수정 후 곡 전체를 다시 재생했고, 후반부에서도 노트와 음원의 싱크가 유지되는 것을 확인했습니다.

당시에는 수정 전후의 오차를 자동으로 측정하지 않고 문제가 발생한 곡을 직접 재생해 결과를 확인했습니다. 앞서 제시한 `155ms`는 정밀도 손실이 누적되는 원리를 설명하기 위한 계산 예시이며 실제 측정값은 아닙니다.

## 회고

처음에는 화면에서 직접 보이는 노트 이동 로직을 원인으로 판단했습니다. 첫 수정으로 문제가 완전히 해결되지 않자 노트 생성 로직을 확인했고, 그곳에서도 원인을 찾지 못한 뒤 생성에 사용되는 채보 데이터와 시간 산출 과정까지 추적했습니다.

특히 시간 관련 변수를 `float`로 변경한 뒤에도 문제를 다시 확인한 과정이 중요했습니다. 변수의 선언만 바뀌었을 뿐 계산식의 정수 변환은 남아 있었고, 잘린 값이 누적되는 구조도 함께 제거해야 했습니다. 이를 통해 값의 최종 자료형만 확인하는 것이 아니라 값이 생성되고 전달되는 전체 계산 경로를 살펴봐야 한다는 점을 배웠습니다.

또한 첫 번째 가설이 문제의 일부만 설명할 수 있다는 사실을 수정 결과로 확인했습니다. 첫 수정에 머무르지 않고 남은 현상을 기준으로 조사 범위를 넓히면서, 서로 다른 시간 기준과 수치 정밀도 손실이라는 복합적인 원인을 분리해 해결할 수 있었습니다.
