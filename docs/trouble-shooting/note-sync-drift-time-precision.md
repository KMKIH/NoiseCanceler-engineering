# 곡 후반으로 갈수록 노트가 음원보다 앞당겨지는 문제

## 문제 현상

노트는 생성 지점에서 판정 지점까지 정해진 시간 동안 이동한다. 짧은 구간을 반복해서 확인할 때는 노트와 음악이 정상적으로 맞았지만, 곡 전체를 재생하면 뒤로 갈수록 노트가 음악보다 점차 빨라졌다.

특정 노트나 마디에서 갑자기 싱크가 어긋나는 것이 아니라 곡이 진행될수록 오차가 커졌다. 따라서 개별 채보 데이터보다 반복되는 시간 계산에서 작은 차이가 누적되고 있을 가능성이 높다고 판단했다.

## 원인 추정 1: 노트 이동과 음원의 시간 기준 불일치

기존 노트는 Unity의 `Time.time`으로 생성 후 경과 시간을 구하고, 경과 시간과 이동 속도를 이용해 위치를 계산했다.

```csharp
double timeSinceStart = Time.time * 1000 - startTime;
float moveDistance = (float)(timeSinceStart * speed);
transform.position = startPoint.position + Vector3.left * moveDistance;
```

반면 음원은 오디오 시스템의 재생 시간에 따라 진행됐다. 노트와 음악이 서로 다른 시계를 사용하므로, 프레임 지연이나 두 시간값의 갱신 차이가 발생하면 노트의 위치가 음악과 어긋날 수 있는 구조였다.

이를 첫 번째 원인으로 추정하고 노트의 생성 시각과 현재 시각을 음원 재생 시간으로 통일했다. 매 프레임 이동량을 더하는 대신, 현재 음원 시간이 전체 이동 구간에서 차지하는 비율로 절대 위치를 계산했다.

```csharp
double curTime = dataManager.SheetData.songPosition;
double ratio = (curTime - startTime) / takeTime;

transform.position = Vector3.LerpUnclamped(
    startPoint.position,
    judgePoint.position,
    (float)ratio);
```

프레임이 잠시 지연되더라도 다음 프레임에는 현재 음원 시간에 해당하는 위치를 다시 계산할 수 있게 됐다. 그러나 수정 후에도 곡 후반으로 갈수록 노트가 앞당겨지는 현상은 개선되지 않았다. 노트와 음원이 서로 다른 시간 기준을 사용하는 코드는 잘못된 구현이었지만, 이번 문제의 근본 원인은 아니었다. 따라서 노트의 출현·판정 시각을 만드는 채보 전처리 과정까지 조사 범위를 넓혔다.

## 원인 추정 2: 정수 변환으로 인한 마디 시간 손실

채보 전처리 과정에서는 마디의 길이와 상대 시작 시각을 밀리초 단위의 `int`로 저장하고 있었다. 마디 길이를 계산하는 식에도 정수 변환이 포함되어 있었다.

```csharp
float barTakeTime = (int)(60f / bpm * beatPerBar * 1000);
```

BPM으로 계산한 마디 길이는 소수점 이하 값을 가질 수 있다. 그러나 시간값을 `int`로 저장하거나 계산 중에 `(int)`로 변환하면 소수점 이하 값이 사라진다. 결과를 `float` 변수에 저장하더라도 정수 변환이 먼저 실행되므로 이미 손실된 값은 복구되지 않는다.

예를 들어 한 마디의 실제 길이가 `1777.777ms`인데 `1777ms`로 저장된다면 마디마다 약 `0.777ms`가 손실된다.

```text
한 마디의 시간 손실      약 0.777ms
200마디에서의 손실 예시  0.777ms × 200 ≒ 155ms
```

한 마디만 확인하면 체감하기 어려운 차이지만, 잘린 값을 다음 마디의 시작 시각에 계속 더하면 곡이 진행될수록 채보 시간이 실제 음악보다 점차 빨라진다.

자료형과 계산식을 별개의 문제로 보지 않고, 시간값이 만들어지는 과정에서 발생한 하나의 정밀도 손실 문제로 판단했다. 이에 마디 길이와 상대 시작 시각의 자료형을 `float`로 변경하고, 계산식의 `(int)` 변환도 함께 제거했다.

```csharp
float barTakeTime = 60f / bpm * beatPerBar * 1000;
```

## 추가 조치: 누적 계산 제거

정밀도 손실이 다음 마디로 전파될 가능성도 제거했다. 기존에는 마디 시작 시각을 이전 마디까지 더한 `cumulativeTime`으로 계산했지만, 이를 마디 인덱스와 정확한 마디 길이로 직접 계산하는 방식으로 변경했다.

```csharp
// 기존 방식
relativeStartTime = cumulativeTime;
cumulativeTime += barTakeTime;

// 변경 방식
relativeStartTime = barIndex * barTakeTime;
```

변경 후에는 각 마디의 시작 시각이 이전 계산 결과에 의존하지 않으므로, 앞에서 발생한 오차가 다음 마디로 전파되는 경로가 사라졌다.

수정 후 곡 전체를 다시 재생했고, 후반부에서도 노트와 음원의 싱크가 유지되는 것을 확인했다.

## 회고

반복해서 값을 더하는 구조에서는 한 번의 계산에서 발생한 작은 오차가 이후 계산에 계속 포함된다. 개별 계산의 오차가 눈에 띄지 않을 정도로 작더라도, 누적 횟수가 많아지면 사용자가 체감할 수 있는 차이로 커질 수 있다.

이번 문제를 통해 리듬게임의 시간처럼 정밀도가 중요한 값을 계산할 때는 이전 결과에 값을 계속 더하는 방식보다, 고정된 기준값을 바탕으로 각 시점의 값을 직접 계산하는 방식이 적합하다는 점을 배웠다.
