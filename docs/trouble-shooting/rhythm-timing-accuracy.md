# 음악 시간 계산 오차로 인한 판정 정확도 개선

> 이 문서는 Unity `AudioSource`를 사용하던 시기의 문제 해결 과정을 다룹니다. 현재 FMOD 기반 구현은 [FMOD 기반 리듬게임 시간 동기화 및 판정 시스템](../architecture/rhythm-game-timing-and-judgement-system.md)에 정리했습니다.

## 개요

리듬게임은 음악 재생 시간과 노트 이동, 입력 판정이 동일한 시간 기준에 맞춰 동작해야 합니다. 그러나 프로젝트 초기에는 리듬게임 개발 경험이 부족해, Unity의 `Update()`에서 `AudioSource.time`을 조회하고 이를 현재 음악 시간으로 사용하는 방식으로 판정 시스템을 구현했습니다.

테스트 과정에서 같은 입력을 해도 프레임 상태에 따라 판정 시점이 달라지는 현상이 발생했습니다. 디버깅 결과 `AudioSource.time`이 2~3프레임 동안 같은 값을 반환하는 구간이 있었고, 이로 인해 실제 음악은 재생되고 있지만 판정 시스템의 시간은 잠시 멈춰 있는 문제가 있었습니다.

처음에는 값이 갱신되지 않는 구간의 음악 시간을 최근 프레임 간격의 이동평균으로 예측했습니다. 하지만 변동하는 프레임 간격을 다시 시간 계산의 기준으로 사용했기 때문에, 일관된 판정 시간을 보장할 수 없었습니다. 이를 통해 보정 방법보다 먼저 렌더링 프레임과 독립된 시간 기준이 필요하다고 판단했고, 리듬게임의 음악 시간 처리 방식을 다시 검토했습니다.

이 문서에서는 `AudioSource.time` 기반 구현에서 발생한 문제, 이동평균을 이용한 예측 방식의 한계, `AudioSettings.dspTime` 기반 구조로 변경한 과정을 정리합니다.

## 문제 상황

초기 판정 시스템은 매 프레임 `AudioSource.time`을 조회한 뒤, 현재 음악 시간과 노트의 판정 시간을 비교하는 구조였습니다.

아래 코드는 당시 구현의 핵심 흐름을 설명하기 위해 단순화한 예시입니다.

```csharp
private void Update()
{
    float songTime = audioSource.time;
    JudgeNotes(songTime);
}
```

구현이 단순하고 Unity에서 바로 확인할 수 있는 값을 사용한다는 장점이 있었지만, 음악 시간과 렌더링 프레임의 갱신 주기가 항상 일치하지 않았습니다. 디버깅에서 관찰한 현상을 단순화하면 다음과 같습니다.

```text
렌더링 프레임    F1       F2       F3       F4
AudioSource.time 1.250    1.250    1.250    1.301
판정 시간        정지     정지     정지     한 번에 증가
```

실제 음악은 계속 재생되고 있지만 게임 로직이 참조하는 시간은 여러 프레임 동안 멈췄다가 한 번에 증가했습니다. 따라서 동일한 박자에 입력하더라도 입력이 발생한 프레임에 따라 판정 오차가 달라질 수 있었습니다.

`AudioSource.time`은 오디오 재생 위치를 조회하기에는 편리하지만, 리듬게임의 판정 기준으로 사용하기에는 오디오 처리 및 버퍼 갱신 주기와 렌더링 프레임 사이의 차이를 고려해야 했습니다.

## 첫 번째 시도: 갱신되지 않은 시간 예측

처음에는 `AudioSource.time`이 갱신되지 않는 프레임에 게임 로직에서 직접 시간을 보완하면 된다고 판단했습니다. 프레임 간격이 일정하지 않다는 점을 고려해 최근 `deltaTime`의 이동평균을 계산하고, 마지막으로 확인한 음악 시간에 더하는 방식을 적용했습니다.

```csharp
float estimatedFrameTime = recentDeltaTimes.Average();

if (audioSource.time == previousAudioTime)
{
    estimatedSongTime += estimatedFrameTime;
}
else
{
    estimatedSongTime = audioSource.time;
}
```

이 방식은 음악 시간이 정지해 보이는 구간을 채울 수 있었지만, 다음과 같은 문제가 남았습니다.

- 프레임 간격이 변할 때마다 예측값도 함께 달라졌습니다.
- 이동평균은 과거 프레임을 기반으로 한 추정값일 뿐, 실제 오디오 재생 위치를 나타내지 않았습니다.
- `AudioSource.time`이 다시 갱신되는 순간 예측값과 실제 값 사이의 차이를 처리해야 했습니다.
- 저사양 환경이나 순간적인 프레임 저하에서 오차가 더 커질 수 있었습니다.

가장 큰 문제는 오차를 보정하기 위해 다시 변동하는 프레임 시간을 기준으로 사용했다는 점이었습니다. 계산 방법을 정교하게 만드는 것만으로는 기준 자체가 흔들리는 문제를 해결할 수 없었습니다.

## 원인 분석

노트 판정이 프레임에 따라 달라진 이유는 판정 공식보다 현재 음악 시간을 가져오는 기준에 있었습니다.

```text
Update 호출 시점
    ↓
AudioSource.time 조회
    ↓
노트 판정 시간과 비교
```

이 구조에서는 오디오 시스템의 진행 상태를 렌더링 프레임에서 조회한 값이 판정 기준이 됩니다. 조회값이 같은 상태로 유지되는 프레임에서는 입력 시각도 같은 값으로 처리되고, 다음 갱신에서는 시간이 한 번에 이동합니다.

따라서 다음 조건을 만족하는 새로운 기준이 필요했습니다.

1. 렌더링 프레임 간격과 독립적으로 증가해야 합니다.
2. 음악 재생을 예약하는 시간과 판정 시간이 같은 기준을 사용해야 합니다.
3. 노트 이동과 판정음도 동일한 시간축에 맞출 수 있어야 합니다.

## 해결: DSP 시간을 공통 기준으로 사용

다른 리듬게임 개발 사례와 Unity 오디오 시스템을 조사한 뒤, `AudioSettings.dspTime`을 음악 시간의 기준으로 사용했습니다. `dspTime`은 오디오 시스템이 사용하는 시간을 제공하므로 렌더링 프레임의 변동과 분리해 사용할 수 있습니다.

음악이 시작된 DSP 시간을 저장하고, 현재 DSP 시간과의 차이로 곡의 진행 시간을 계산했습니다.

```csharp
double songStartDspTime;

private void StartSong()
{
    songStartDspTime = AudioSettings.dspTime;
    audioSource.Play();
}

private void UpdateSongTime()
{
    songPosition = (AudioSettings.dspTime - songStartDspTime) * 1000.0;
}
```

이후 노트 이동과 입력 판정은 `AudioSource.time` 대신 계산된 `songPosition`을 참조하도록 변경했습니다.

```text
AudioSettings.dspTime
          ↓
    현재 음악 시간 계산
          ↓
  ┌───────┼────────┐
  ↓       ↓        ↓
노트 이동  입력 판정  판정음 예약
```

이를 통해 렌더링 프레임은 판정 로직을 실행하는 시점만 결정하고, 판정에 사용되는 시간값은 오디오 시스템의 시간축을 따르도록 역할을 분리했습니다.

## 판정음 예약 재생

음악 시간과 판정을 DSP 기준으로 변경해도, 판정음을 `Update()`에서 즉시 재생하면 실제 출력 시점은 해당 프레임의 실행 시점에 영향을 받습니다.

이를 줄이기 위해 노트 판정 시각과 현재 음악 시간의 차이를 계산하고, `AudioSource.PlayScheduled()`를 사용해 DSP 시간에 맞춰 판정음을 예약했습니다.

```csharp
double remainTime = noteJudgeTime - songPosition;
double targetDspTime = AudioSettings.dspTime + remainTime / 1000.0;

judgeAudioSource.PlayScheduled(targetDspTime);
```

판정 시각이 아직 지나지 않았다면 남은 시간만큼 이후의 DSP 시점을 지정하고, 오디오 시스템이 해당 시점에 판정음을 재생하도록 했습니다. 음악 재생 시간, 노트 판정, 판정음이 같은 시간축을 사용하게 되면서 프레임 실행 시점에 대한 의존성을 줄일 수 있었습니다.

## 결과

- `AudioSource.time`의 갱신 간격을 판정 기준으로 사용하지 않게 되었습니다.
- 프레임 간격을 이용해 음악 시간을 추정하던 보정 로직을 제거했습니다.
- 노트 이동과 입력 판정이 동일한 DSP 기반 음악 시간을 참조하도록 구성했습니다.
- 판정음을 즉시 재생하는 대신 DSP 시간에 예약하여 프레임 실행 시점의 영향을 줄였습니다.

별도의 정량 측정 도구를 통해 개선 전후 오차를 수치화하지는 못했기 때문에, 이 문서에서는 정확도가 특정 수치만큼 향상되었다고 표현하지 않습니다. 다만 판정 시간의 기준이 렌더링 프레임에 종속되던 구조를 제거하고, 음악과 판정에 공통으로 사용할 수 있는 시간 기준을 마련했습니다.

## 한계와 후속 변경

DSP 시간을 공통 기준으로 사용하더라도 실제 사용자가 듣는 시점에는 운영체제, 오디오 드라이버, 출력 장치의 지연이 포함될 수 있습니다. 따라서 DSP 시간 적용만으로 사용자별 입력·출력 지연까지 모두 해결할 수는 없으며, 별도의 입력 오프셋 보정이 필요했습니다.

또한 이 문서에서 설명한 내용은 Unity `AudioSource`를 사용하던 시기의 문제 해결 과정입니다. 이후 프로젝트에 FMOD를 도입하면서 현재 구현은 다음과 같이 변경되었습니다.

- 음악 진행 시간: FMOD `EventInstance.getTimelinePosition()` 사용
- 판정음 예약: FMOD DSP Clock과 `ChannelGroup.setDelay()` 사용
- Timeline 연출: FMOD 음악 재생과 분리한 뒤 별도 동기화

현재 시스템의 전체 구조와 클래스별 책임은 [FMOD 기반 리듬게임 시간 동기화 및 판정 시스템](../architecture/rhythm-game-timing-and-judgement-system.md)에서 다룹니다.

## 회고

처음에는 값이 갱신되지 않는 현상만 해결하려 했기 때문에, 기존 값 사이를 예측해서 채우는 방법을 선택했습니다. 그러나 실제 문제는 예측식의 정확도가 아니라 판정의 기준으로 사용한 시간이 프레임과 오디오 처리 주기의 영향을 받고 있다는 점이었습니다.

이 경험을 통해 시간에 민감한 시스템에서는 보정 로직을 추가하기 전에 다음 내용을 먼저 확인해야 한다는 점을 배웠습니다.

- 현재 시간값은 어느 시스템의 시간인가?
- 해당 시간은 어떤 주기로 갱신되는가?
- 함께 동작하는 기능들이 같은 시간축을 사용하는가?
- 프레임 저하가 발생해도 기준 시간 자체는 유지되는가?

리듬게임의 판정 시스템을 구현하는 데 중요한 것은 매 프레임 값을 빠르게 계산하는 것이 아니라, 음악·노트·입력·사운드가 공유할 수 있는 기준 시간을 명확하게 정하는 일이었습니다.
